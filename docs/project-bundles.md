# 项目部署包

`.ssdev-project` 是面向实施交付的项目迁移单元，包含当前有效桌面配置、所有已验证签名插件和本机动态映射。它解决的是配置机到目标 Windows 机器的可重复迁移，不替代客户端 NSIS 安装包。

## 控制台流程

控制台把交付固定为源机准备、目标机导入和 Windows 实机验证三步，避免把未签名草稿误当成可安装项目包：

1. **源机导出交付草稿。** 在配置机先填写项目名称和稳定项目标识，再完成项目地址、签名插件和本地映射配置，然后进入“项目交付”，选择“导出项目包草稿”。导出先要求磁盘完整清单与控制器激活快照一致，再确定性封装组件并从这些待写入项目包的精确候选重新解包，检查联合服务路由和来源授权覆盖，并为每种实际架构启动隔离宿主完成无业务副作用的预检；通过后显示整个项目包的 SHA-256。
2. **组织签名并在目标机预检。** 由组织发布系统根据同一 SHA-256 生成 detached 签名封套。将 `.ssdev-project` 和对应的 `.ssdev-project.sig.json` 一起交付，在目标 Windows 机器选择“选择已签项目包并预检”。此时只执行读取、组织签名、组件验签、路由检查和宿主预检，不修改当前项目；核对配置变化和组件新增、升级、同版本修复、替换以及目标机包外能力后，才确认原子导入。包外能力必须先逐项处理或纳入项目包，不能直接带入新项目。
3. **目标机完成深度验证。** 导入成功后打开真实业务环境，确认页面已到达 Rust IPC，再在同一“项目交付”工作区执行“深度自检”并导出现场记录。深度自检会验证目标机实际 x86/x64 宿主；非 Windows 开发预览不提供这一交付结论。

控制台把正在编辑的配置草稿与磁盘中的当前有效配置分开跟踪，并使用对象键顺序无关、数组顺序敏感的确定性摘要识别实际变化。存在未保存草稿时，业务启动、配置/项目导出、项目包预检、插件与本地映射变更以及部署自检都会暂停；界面只允许显式保存或放弃草稿，不能让这些操作静默消费旧配置。关闭控制窗口也会触发未保存保护。普通配置导入可以在一次明确提示后预检，取消仍保留草稿，只有确认导入成功才用后端返回的有效快照替换草稿；项目包在预检后若又产生草稿，最终导入前必须再次确认覆盖。这样项目包的“当前配置”始终指已经持久化并参与来源授权检查的配置，而不是表单中尚未提交的地址。

## 包结构与信任边界

项目包使用受限 ZIP 容器，固定包含：

- `project.json`：schema、创建客户端版本、配置摘要以及组件 ID、类型、版本、大小和 SHA-256；
- `config.json`：通过 `ssdev-config` 完整校验的桌面配置；
- `components/*.ssdev-plugin`：从已安装目录重新生成的确定性签名插件包；
- `components/*.ssdev-mapping`：本机管理员创建的动态映射及其组件。

`config.json` 中的 `projectName` 是面向实施人员的 1–128 字符显示名称，`projectId` 是以字母或数字开头、最多 64 位且只含 ASCII 字母、数字、点、短横线和下划线的稳定标识。两者必须同时配置才能进入项目交付。现有未命名配置可以继续启动业务，以免升级后阻断现场使用，但不能导出项目包、导入匿名项目包或通过部署交付检查。项目身份会被配置摘要和项目包旁签共同覆盖，不能在签名后替换；它不参与 SSO，也不授予任何来源或原生能力。

项目包最多包含 128 个组件，单组件最大 1 GiB，容器及解压内容最大 4 GiB。组件 ID 在所有平台都按 Windows ASCII 大小写不敏感规则判定身份，因此 `reader` 与 `Reader` 不能同时出现；声明拼写会保留，但项目包创建、读取、目标机差异计算和导入事务都不会自动改名。签名插件必须声明有效 SemVer，本地映射不得伪装成带发布版本的签名产物；这组类型/版本规则同时用于原始输入、最终容器写入和读取，不能通过复制或重排已经预检的中间输入绕过。最终写入还会重新规范排序和检查 ID 唯一性，确保相同内容不因调用顺序产生不同项目包。读取过程拒绝覆盖、重复条目、未声明文件、路径穿越、符号链接、特殊文件、摘要不一致和非规范插件 ID。

项目包使用独立的 `project-bundle` 信任用途，签名 payload 为 ASCII `SSDEV-PROJECT-BUNDLE`、一个 `0x00` 字节，再拼接整个 `.ssdev-project` 原始文件的 SHA-256（二进制 32 字节）。因此配置、本地映射、内部签名插件、清单、ZIP 元数据或重新封包中的任意变化都会使旁签失效；内部签名插件仍会逐个执行自身的组织签名和完整文件清单验证，两层信任不能相互替代。

控制台只导出未签名草稿，不持有生产私钥。正式交付使用 [统一发布文档签名](release-signing.md) 的外部 KMS/HSM 流程：

```powershell
cargo run --locked -p ssdev-release-signing -- prepare `
  --kind project-bundle `
  --document C:\secure-release\clinic.ssdev-project `
  --key-id project-delivery-2026-01 `
  --trust-store C:\secure-build-inputs\plugin-trust.json `
  --request C:\secure-release\clinic.project.signing-request.json

# KMS/HSM 对请求中的 payloadBase64 解码结果签名后：
cargo run --locked -p ssdev-release-signing -- finalize `
  --kind project-bundle `
  --document C:\secure-release\clinic.ssdev-project `
  --request C:\secure-release\clinic.project.signing-request.json `
  --signature C:\secure-signing-output\clinic.project.sig.base64 `
  --trust-store C:\secure-build-inputs\plugin-trust.json `
  --envelope C:\secure-release\clinic.ssdev-project.sig.json
```

正式客户端按固定规则在项目包同目录查找 `<完整项目包文件名>.sig.json`，例如 `clinic.ssdev-project.sig.json`。缺少封套、用途不匹配、签名无效、密钥已吊销或项目包在读取期间变化时，预检会失败关闭；运行时为计划轮换继续接受 `retired` 有效签名。只有显式启用未签名插件的 Debug 模式可预检未签名项目包，不能用于正式交付。

导出门禁只覆盖能由项目内容和当前原生运行态证明的可移植条件：配置与来源策略、组件完整性、联合路由、来源—方法双向授权覆盖、活动服务对账和候选宿主启动。门禁绑定的是确定性封装后的组件，而不是封装前可能被外部工具改动的工作目录；项目容器复制组件时还会同时复算大小和 SHA-256，任何两阶段文件漂移都会在目标文件持久化前失败。成功提示中的项目包 SHA-256 必须与外部 `prepare --kind project-bundle` 签名请求里的 `documentSha256` 一致，交付人员不应仅凭文件名判断草稿。在线更新、诊断导出、目标机网络、SSO、院内证书及真实 DLL/COM 方法结果仍应在目标 Windows 机器验收；这些机器特定条件不会阻止配置机生成项目包。空项目也允许导出，部署自检会继续把“没有原生服务”作为提醒而不是失败。

## 预检与导入语义

只读预检在修改目标机器前完成以下工作：

- 校验项目配置和当前来源策略；
- 验证覆盖整个项目包的 `project-bundle` 组织签名；
- 核对组件清单、大小和 SHA-256；
- 验证每个发布插件的身份、版本、完整文件清单和签名密钥状态；
- 要求每个发布插件显式声明并匹配目标机器当前 SSDEV Desktop SemVer；
- 拒绝默认插件降级；
- 验证本地映射定义和组件路径；
- 拒绝同一 ID 在签名插件和本地映射之间隐式换型；
- 以项目包声明的精确组件集合检查服务路由冲突；
- 将目标配置中的全部业务来源与项目包规范方法名和 alias 做双向授权覆盖核对；
- 启动候选 x86/x64 隔离宿主完成真实预检。

预检不会把项目包组件简单罗列为“将安装”。它会与当前机器状态比较：不存在的组件标为“新增”，更高版本签名插件标为“升级”，同版本签名插件标为“同版本修复”，已有本地映射标为“替换映射”；未在项目包中声明的现有签名插件和本地映射单独列为“包外能力”。只读预检仍会展示完整列表，但导入按钮和后端提交命令都会失败关闭，直至包外数量为零。

项目配置复用普通 JSON 导入的同一份差异模型。本地控制窗口会先明确展示当前与目标项目名称/标识，再展示目标默认业务入口、环境列表，以及业务/SSO/外链来源、受控进程和启用快捷键的当前值到目标值；同时标明租户、环境切换、关闭确认、开机启动和插件仓库是否变化及目标开关状态。业务地址和环境名称只返回给受限本地控制窗口用于人工确认，结构化日志仍只记录配置是否变化及数量，不复制项目身份、URL、租户或其他配置内容。项目包的整体计划标识仍是唯一确认凭据，配置摘要本身不产生第二个可独立提交的计划 ID。

普通配置保存或导入不适合把机器从一套插件能力切换到另一套项目来源：当业务来源集合变化时，客户端会先以控制器当前活动的签名插件清单检查候选来源，任何现有路由失去全部授权都会在关闭业务窗口或写配置前失败。项目部署包则用候选配置与候选组件联合计算授权覆盖，并在同一持久事务中切换两者；因此需要同时增删来源和插件的正式项目切换必须使用项目包，而不是先改配置、再逐个安装插件。

每次预检还生成一个只在本次确认中使用的导入计划标识。它以域分隔 SHA-256 绑定项目包全部原始字节、当前 Desktop 版本、当前已保存配置、签名插件完整签名载荷以及本地映射确定性包。控制台确认导入时必须提交该标识；客户端在插件安装锁内重新打开项目包、恢复事务、重建当前状态摘要并重新执行全部预检，只有计划标识完全一致才进入任何目录或配置变更。项目包被替换、配置被保存、插件/映射发生安装、更新、卸载或内容变化时，旧确认都会失败并要求重新预检。

确认命令完成上述重建后，还会在创建项目事务前再次读取完整插件/映射清单、重算配置与能力内容摘要，并核对控制器活动路由与磁盘清单一致。这样即使外部进程恰好在确认重建结束后改动能力目录，也不能沿用刚刚计算的精确集合结论开始切换；这一复核不自动加载外部变化，漂移时要求安全重扫、重启或重新预检。

计划标识复核通过且目标机不存在包外能力后，客户端才写入项目级持久事务，再进入一次全局维护窗口，将项目包声明的签名插件和本地映射切换到候选目录、重新发现精确组件清单并一次替换控制器路由，最后切换项目配置。组件激活后先要求已验证清单与项目包声明逐项一致；配置和路由已经切换但持久提交点尚未写入时，再读取一次磁盘能力，复算目标配置与全部组件内容摘要，并核对活动路由。如果此时出现新增、缺失、内容变化、隔离项或路由漂移，客户端恢复旧配置、旧路由和全部组件后要求重新预检。任一组件、联合路由或配置切换失败也按相反顺序恢复，不会留下“部分插件已升级但仍使用旧配置”的混合状态。

只有项目事务提交点写入成功后，客户端才程序化销毁旧业务窗口及其悬浮页面。这项销毁不经过面向用户手动关闭的 `autoClose` 确认，避免项目已切换却仍保留旧页面；若个别 WebView 销毁失败，导入结果按请求、成功和失败数量如实提示手动关闭，但不把已越过持久提交点的项目误报为回滚。提交点之前失败时不销毁现有业务工作区。

控制台中的原生映射编辑器可能同时持有尚未保存的现场草稿。确认项目导入前会单独提示这项本地状态；用户取消时不调用导入命令。只有项目导入命令成功后才重建映射工作台并从磁盘读取新清单，命令失败时保留原草稿，避免预检、失败重试或普通页面切换造成静默丢失，也避免导入成功后继续展示旧映射。

项目事务以一次原子重命名记录统一提交点。提交点之前崩溃或断电，下次启动恢复旧配置并回滚全部未提交组件；提交点之后崩溃，则保留新配置并完成全部组件事务清理。签名插件与本地映射都使用有界、单组件 ID 的持久日志，恢复过程可重复执行。运行中发现需要恢复旧配置的未提交项目事务时会要求重启，避免只修改磁盘配置而让内存配置继续停留在新版本。

项目包导入不会自动删除未声明的现有插件或映射，也不会让这些能力继续混入目标项目。目标机存在包外能力时，预检保持只读并明确阻断导入；管理员必须在“插件管理”或“原生映射”中逐项确认卸载/删除，或者回到源机重新生成包含这些能力的项目包，然后再次预检。两条删除路径都有独立影响预览、按插件维护和可恢复事务，不能因为项目包没有声明某个组件就隐式触发破坏性操作。现阶段客户端只维护一个活动项目工作区，因此项目包代表该项目的完整能力集合；后续只有在出现明确的多项目共存需求和所有权模型后，才评估受控同步模式。
