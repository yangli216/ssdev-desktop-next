# 产品定位与迭代准则

## 定位

SSDEV Desktop 是面向 Windows 行业应用的 Web 本地能力运行与项目交付平台。它让受控 B/S 业务系统通过稳定的 Web Bridge 调用 DLL、COM/OCX、硬件设备和必要的操作系统能力，同时把插件、项目配置、部署策略、测试矩阵和更新治理纳入同一条可验证交付链。

产品不以“替代通用浏览器”或“支持尽可能多的原生接口”为目标。核心结果是：业务开发不需要理解桌面 IPC，实施人员可以重复交付项目，第三方原生组件故障不会拖垮桌面主进程，运维人员能够验证、升级、回退和定位现场问题。

## 主要用户与默认入口

| 用户 | 核心任务 | 产品默认体验 |
| --- | --- | --- |
| 普通业务用户 | 打开当前业务环境并完成工作 | 首页进入业务系统；不要求理解插件、签名或 ABI |
| 项目实施人员 | 配置环境、映射原生能力、调试并交付项目 | 项目配置、原生映射、部署自检和项目部署包 |
| 插件开发人员 | 封装复杂厂商组件并交付类型化 Web API | 插件脚手架、源检查、SDK、fixture 和黄金矩阵 |
| 发布与运维人员 | 签名、发布、升级、回退和诊断 | 插件仓库、应用更新、诊断以及生产切换证据 |

远程业务页面只获得运行项目所需的窄能力。本地控制台承担实施和管理任务，两者不能因为界面便利而合并权限边界。

## 优先级

### P0：真实项目试点闭环

在增加新能力之前，优先用真实 Windows 项目证明现有链路：

1. 使用生产 DLL、COM/OCX、驱动和代表性硬件建立覆盖全部公开方法的脱敏黄金矩阵。
2. 使用业务前端静态产物和代表性 HAR 关闭旧 `7711`、`45121` HTTP 依赖结论。
3. 接入组织插件/策略签名、Windows Authenticode 和 Tauri updater 密钥，不把仓库测试密钥用于交付。
4. 使用上一生产安装包完成安装、原位升级、配置与本地能力数据根保留、失败回退和卸载演练。
5. 由独立环境生成插件矩阵、迁移审计和 Windows 包证据，通过 Go/No-Go 后才切换旧 Electron/WebPlus。

完成标准不是“代码测试全部通过”，而是另一名实施人员能够根据受控材料独立完成部署、验证和恢复。

### P1：项目交付效率

只建设能明显减少每个项目重复劳动的能力：

- 项目配置、签名插件、本地映射和来源策略的联合预检与原子项目包；
- DLL/COM 可视化发现、配置、现场调试、回归用例和发布源导出；
- 一键快速/深度部署自检以及稳定、可行动的诊断码；
- 插件和 Desktop 版本兼容门禁、受控安装、升级、撤回与回退；
- 从同一 API 清单生成 TypeScript 客户端、fixture 和可复核 Web 接入包。

新需求如果只能改善少量人工操作、却增加新的运行时协议或信任边界，应先保留为项目模板或专用插件，不进入平台核心。

### P2：可复用插件体系

只有在多个真实项目已经复用同类组件后再投入：

- 常用设备或厂商的专用 Rust 适配器模板；
- 企业内部签名插件目录和兼容性认证；
- 可离线部署的组织级版本治理与发布审计；
- 基于真实项目数据确定的稳定 SDK 扩展，而不是提前设计通用市场。

## 暂不投入

- macOS/Linux 生产能力：保留开发预览，不承诺 Windows DLL/COM 等价能力。
- Windows 7 主线兼容：只有明确交付需求时建立冻结依赖、独立验证的 LTS 分支。
- 通用浏览器功能：书签、下载中心、复杂标签管理等不属于核心运行与交付价值。
- 任意 Shell、任意 JavaScript 注入、通用本机 HTTP 服务或 Tauri 主进程直接加载第三方 DLL。
- 为罕见 ABI 持续扩张可视化表单：复杂结构体、回调、厂商内存管理和线程模型进入专用 Rust 适配器。
- 强依赖公有云的管理平台：客户以院内 HTTP、隔离网和半离线环境为主，后续治理优先支持本地或私有部署。
- 在没有多项目复用证据前建设大型插件市场、低代码平台或跨组织生态。

## 工作选择规则

每项核心迭代至少应明确改善以下一项，并具有相应验证证据：

1. 降低真实项目从旧 WebPlus 迁移到无 localhost HTTP 架构的风险；
2. 提高 DLL/COM/硬件调用的隔离性、正确性或可恢复性；
3. 缩短项目配置、调试、打包、部署和验收时间；
4. 提高插件、应用更新和生产切换的可追溯性；
5. 让业务开发通过稳定 SDK 接入，而不是复制桌面私有实现。

若需求无法落入这些结果，应优先放入项目插件、示例或文档，或明确暂缓，不直接扩张核心运行时。

## 当前阶段

当前处于“工程链路基本完成、等待真实业务验收”的阶段。自动门禁可以证明合成 DLL/COM、双架构宿主、签名包、安装升级和证据工具链，但不能替代生产组件、硬件、账号网络、组织密钥和上一生产安装包。近期迭代因此以真实试点输入收集、Windows 实机结果和现场可恢复性为唯一 P0，不以新增能力数量衡量进度。

真实试点还必须证明“窗口已创建”之后业务页面确实可用。业务 WebView 在每次返回已配置业务来源时自动完成页面到 Rust IPC 的就绪握手；30 秒未到达即以稳定错误码提示网络、代理或证书方向，并进入首页状态、深度交付门禁和脱敏诊断。SSO 等受信任跳转只显示为导航中，不被误判为业务页面超时。后续同类迭代优先补真实路径证据和恢复动作，不再以增加低频原生接口数量作为进度。

普通用户入口也必须服从这一定位：存在已授权默认业务地址时，正常启动、重复启动和托盘左键都优先进入或恢复业务窗口，管理控制台在后台保持可恢复但不抢占首屏。没有配置、业务窗口创建失败、SSO 处理需要反馈或登录失败时才显示控制台；业务页面就绪超时的原生提示确认后也直接打开控制台中的定向重试与诊断入口。这不是隐藏错误，而是把管理界面从普通业务路径中移出。控制台只有在托盘真实存在时才将关闭解释为隐藏，否则保留正常退出路径。

这条普通用户主路径必须进入 Windows 候选包门禁，而不是只依赖源码契约。CI 在隔离账号写入签名策略允许的惰性测试地址，要求候选安装后同时出现隐藏控制前端 IPC 和无 URL 的业务窗口创建事件；旧版回装只保留原有启动要求，避免用新事件淘汰合法上一生产版本。业务窗口创建仍不等于页面可用，目标网络的真实业务页握手和深度检查继续是正式交付证据。

这项运行时事实还必须进入发布证据，而不是停留在现场截图：正式 Windows QA 将同版本客户端近期导出的深度部署记录摘要绑定进 schema 7 包证据，最终 Go/No-Go 对缺失真实业务页握手稳定 NO-GO。普通 CI 保持空绑定，只证明安装脚本，不冒充目标网络验收。

现场可恢复性同样不能由“候选升级成功”推断。Windows 门禁会卸载候选并回装指定上一生产 bundle，复核上一版本签名、布局和实际启动；从上一版首次启动到候选升级、卸载、旧版回装及最终卸载，还会持续复核配置字段以及插件、本地映射数据根哨兵，阻止安装链整体清理现有能力数据。schema 7 将回退结果、升级结果与 `applicationStatePreservationVerified` 分开记录，最终判定缺少回退或状态保留时分别稳定 NO-GO。该演练限定在客户端安装层，真实插件内容和设备或业务系统的非幂等副作用仍需项目黄金矩阵及业务对账处理。

试点输入以 [真实项目试点材料预检](pilot-readiness.md) 建立可移交基线。它只读绑定材料集合、正式迁移审计角色并明确缺项；正式审计只能从已复验移交派生输入，不能用另一组手工样本替代。该链路不新增远程协议或桌面权限，也不会把“文件齐全”误报为生产就绪。

实施与 QA 工具也不应继续依赖每台验证机临时安装 Rust，或为了方便被塞进普通用户 NSIS。Windows 主线单独发布 x64 项目交付工具包，承载试点预检、迁移审计、插件发布、组织签名、切换判定和正式黄金矩阵运行器；工具包记录源码提交和完整文件清单，生产 EXE 逐个完成 Authenticode，最终归档再由组织发布系统签名后分发。它不包含私钥、项目材料或候选安装包，仍要求黄金矩阵绑定同一干净源码与候选双架构宿主。这样缩短每个项目的环境准备时间，同时不增加在线轻量版体积、普通业务终端权限或新的运行时协议。

生产切换策略同样从这套已复验材料、候选/上一生产 bundle、插件发布集合和组织公开信任材料自动派生不可覆盖的项目事实；人员只批准覆盖下限、证据时效、最长七天的 GO 执行窗口和职责分离。策略先由现有最终审批职责使用独立域签名，判定器再把策略封套、QA 证据信任库与最终审批信任库按原始字节写入 GO 决策，同名 keyId 不能替代获准公钥；现场部署前还必须复验完整归档、组织当前受保护的审批与 QA 信任库、实际待安装 Windows bundle 并确认 GO 仍在批准窗口内，确保审批后紧急吊销、误拿另一构建或安装器被替换都可以即时阻止部署。近期不建设新的策略编辑 UI，优先用确定性工具消除每个试点都会重复发生的摘要复制、错版本、替换策略、换信任根和旧审批重放风险。
