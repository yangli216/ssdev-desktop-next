# WebPlus 插件签名规范 v1

生产版只加载通过 Ed25519 验签的插件。客户端只携带公钥，私钥必须保存在发布流水线、KMS 或 HSM 中，不能进入源码、安装包或开发者电脑上的桌面客户端。

## 插件目录与安装包

每个插件目录必须包含：

- `api.json`
- `plugin.json`
- DLL、OCX、EXE、BAT 及其依赖文件
- `plugin-signature.json`

签名清单必须覆盖插件目录中的每一个普通文件，唯一例外是 `plugin-signature.json` 自身。目录中出现未登记文件、文件缺失、内容被修改或符号链接时，插件都会被隔离。

```json
{
  "schemaVersion": 1,
  "keyId": "production-2026-01",
  "algorithm": "ed25519",
  "pluginId": "reader-plugin",
  "files": {
    "api.json": "<lowercase sha256 hex>",
    "bin/reader.dll": "<lowercase sha256 hex>"
  },
  "signature": "<base64 ed25519 signature>"
}
```

`plugin.json` 提供签名覆盖下的插件身份和语义版本：

```json
{
  "schemaVersion": 1,
  "pluginId": "reader-plugin",
  "version": "2.3.1",
  "desktopVersionRequirement": ">=0.1.0, <0.2.0",
  "displayName": "读卡器插件"
}
```

`version` 必须是合法 SemVer。`desktopVersionRequirement` 使用 SemVer requirement 语法，声明该插件经过验证的 SSDEV Desktop 版本范围，最长 128 字符；它与版本、清单一起进入签名覆盖，发布后不能由仓库单独改写。新发布必须显式声明范围，不应使用 `*` 代替兼容性验证。为迁移诊断，运行时仍可解析缺少该字段的旧元数据，但会隔离该插件，正式目录生成和签名也会拒绝它。

安装器默认允许同版本修复和向上升级，但拒绝降级；同时要求候选范围匹配当前 Desktop 版本。生产回退应发布一个版本号更高、内容回到已知稳定实现的新签名包，从而保留单调、可审计的发布历史。

路径统一使用 `/`，文件表按路径的 UTF-8 字节升序排列。`pluginId` 必须与插件目录名一致。

可交付文件使用 `.ssdev-plugin` 扩展名，本质为 ZIP。ZIP 根目录直接放置上述文件，不能再套一层插件目录：

```text
reader-plugin.ssdev-plugin
├── api.json
├── plugin.json
├── plugin-signature.json
└── bin/
    └── reader.dll
```

控制台中的“选择签名插件”不会立即安装。客户端先把包解压到插件根目录下的隐藏暂存目录，检查压缩包大小、条目数、路径穿越、符号链接、Windows 保留路径、重复路径、完整文件清单、Ed25519 签名、Desktop 兼容范围、防降级、联合路由和当前活动路由一致性，并要求安装后的每条签名插件规范方法及 alias 至少被一个当前配置业务来源授权，再完成候选宿主预检。界面只展示插件身份、当前到目标版本、安装/升级/同版本修复动作、服务/方法和宿主计数，不公开所选文件路径或签名 keyId；授权失败只报告未覆盖路由数量，不回显具体来源或路由。

预检产生的确认标识绑定候选目录的规范签名载荷、目标插件当前已安装签名载荷和 Desktop 版本。用户确认后，安装命令在插件安装锁内重新打开、解包和验签原文件，重新检查本机状态、当前来源授权覆盖并精确匹配确认标识；随后进入激活前还会再次核对目标插件基线。文件被替换、目标插件被安装/更新/卸载、当前路由与磁盘发生漂移时都要求重新选择和预检。只有全部复核成功才进入该插件自己的短维护窗口，等待它正在执行的调用结束、只关闭它的 x86/x64 宿主，并以同卷目录重命名完成原子安装或覆盖升级。其他插件的调用和宿主不参与这次排空。

进入排空后，控制器以按插件串行的维护门和维护代次保护该插件的路由/目录切换。发往目标插件的新调用以及开始于旧代次、排在写锁后的迟到调用都以 `ResCode=-32010` 返回并保证未执行，不占用全局调用容量，也不会落到新插件版本上；发往其他插件的调用继续使用各自生命周期和宿主。维护守卫被取消或错误提前释放时会自动恢复目标插件的运行状态。显式“重新扫描插件”、应用退出和本体更新仍使用全局生命周期门，以便一次性替换完整路由集或停止全部宿主。

候选预检为该插件声明的每种架构各启动一个真实隔离宿主；x86 与 x64 宿主并行完成宿主位数选择、Windows Job Object、双方 PID 认证的命名管道、宿主二次验签、清单解析、原生 STA 线程创建和 Health 往返，然后立即停止。Health 只有在对应架构的原生初始化成功后才返回：DLL 及其依赖实际 `LoadLibrary` 并逐项解析声明导出，因位数错误、依赖缺失或导出不存在会失败；COM/OCX 实际初始化 STA、创建声明类并解析方法/属性名，未注册或位数不匹配会失败；EXE/BAT 不启动进程，但会把入口 SHA-256 与宿主二次验签得到的发布清单逐项匹配，并在 Windows 宿主生命周期内持有禁止写入和删除的只读共享句柄。每次真实启动前还会从同一路径重新读取并复算 SHA-256，内容漂移会在创建子进程前失败关闭。它同时持有全局和目标插件的生命周期读锁，但不修改活动路由、也不停止健康宿主，因此其他插件调用可继续；退出、全局重载或同一插件的维护会等待/拒绝这次预检，不同插件的维护不会制造无关停机。显式“重新扫描插件”也必须先对全部有效清单逐个完成该预检，任一失败都保留原活动路由，不会把人工复制但无法启动的目录直接加载。预检不会调用任何 DLL 导出或 COM 方法，也不会启动 EXE/BAT，避免读卡、打印等非幂等业务副作用；真实参数 ABI、返回值和硬件行为仍由生产插件黄金矩阵验证。

进入目标插件维护窗口并移动目录后，新目录会再次发现、验签并验证完整服务路由，再只替换该插件的路由并提交持久事务。新增服务若与其他插件冲突，会在删除旧路由之前失败并回滚，因此无关路由始终保持原子可见。暂存预检到激活之间的文件变化仍会被二次验签发现并回滚；耗时最长的宿主启动不占用维护写锁。

候选宿主预检失败不会修改旧目录或旧路由；进入维护后的激活、二次验签、路由或提交失败则恢复旧目录和旧路由。成功后直接热加载，无需重启桌面端。“重新扫描插件”可用于受控运维恢复，但不会绕过签名或当前来源授权覆盖。预检成功的架构宿主数量和失败次数只以计数进入状态页和诊断包。

安装切换还使用同卷的持久事务目录。事务日志先落盘，旧目录才会移动；只有路由验证成功后，事务目录才以一次原子重命名变成“已提交”状态。因此，即使进程崩溃或设备在任意两个文件操作之间断电，下次启动也会遵循确定性规则：未提交升级恢复旧目录，未提交的新装删除候选目录，已提交但未清理的事务只清理备份。恢复过程自身可重复执行，不会把已经恢复的旧版本再次删除。启动、重新扫描和下一次安装都会先执行恢复，异常事务数量只作为脱敏计数进入状态页和诊断包。

签名插件的卸载沿用同一套按插件维护和持久事务，而不是直接递归删除目录。控制台确认后，客户端只排空目标插件、把其目录移入未提交事务、重新核对联合清单，再原子移除对应路由并提交删除；无关插件和宿主继续服务。路由切换前失败或进程崩溃会恢复原目录，提交后崩溃只完成备份清理。卸载命令仅授权给内置控制窗口，业务 WebView 不能枚举、安装、更新或卸载插件。

事务日志限制为 64 KiB，只接受固定 schema、单段可移植插件 ID 和真实目录；符号链接、路径穿越、重复未完成事务或无法判定的目录状态会让恢复失败并停止插件发现，而不会猜测性删除文件。插件根目录是应用专用数据目录，运维工具不得在其中创建以 `.activation-`、`.committed-` 或 `.staging-` 开头的自定义目录。

## 待签名字节

签名不直接覆盖 JSON 文本，避免不同 JSON 库的字段顺序和空白差异。待签名字节按以下顺序拼接：

1. ASCII 常量 `SSDEV-PLUGIN-SIGNATURE`，随后一个 `0x00`。
2. 一个字节的 `schemaVersion`。
3. `keyId`、`algorithm`、`pluginId`，每项均为“4 字节大端长度 + UTF-8 字节”。
4. 4 字节大端文件数量。
5. 按路径排序的每个文件：路径和小写 SHA-256 十六进制摘要，均使用“4 字节大端长度 + UTF-8 字节”。

发布流水线对这些字节执行 Ed25519 签名，把 Base64 结果写入 `signature`。

生产发布不应人工计算文件表或手工拼 ZIP。仓库提供的 `ssdev-plugin-tool` 会生成外部签名请求、核对签名前后目录未变化、导入单行 Base64 签名、使用公开信任库验签，并制作逐字节可复现的 `.ssdev-plugin`；私钥始终留在 KMS/HSM 或受控 CI。具体流程见 [旧 WebPlus 插件发布迁移](plugin-release.md)。

## 客户端信任库

安装包内的 `plugin-trust.json` 只保存允许的公钥，并为每把密钥声明不可隐式扩大的签名用途：

```json
{
  "schemaVersion": 2,
  "keys": [
    {
      "keyId": "production-2026-01",
      "algorithm": "ed25519",
      "publicKey": "<base64 32-byte public key>",
      "purposes": ["plugin"],
      "status": "active"
    }
  ]
}
```

允许的用途只有 `plugin`、`plugin-catalog`、`project-bundle`、`origin-policy`、`process-policy`、`cutover-evidence` 和 `cutover-decision`。生产环境应为插件运行时、仓库发布、项目交付、QA 执行证明和切换审批使用不同密钥；确需合并时必须在 `purposes` 中显式列出，不能因为公钥存在就跨用途验签。

`status` 用于管理密钥生命周期：

- `active` 可验证历史产物，也可被发布工具用于签发新插件、目录和策略。
- `retired` 让官方发布工具停止签发，同时让运行时继续接受该公钥的有效签名，用于计划轮换期间保持兼容。
- `revoked` 对历史和新产物都立即失败，用于确认泄露或误签后的紧急阻断。

为兼容已发布的 schema 2 信任库，省略 `status` 等同于 `active`。正常轮换必须先同时加入新的 `active` 密钥，再把旧密钥改为 `retired`；确认所有仍需运行的历史插件和策略都已迁移后才能移除旧密钥。Ed25519 签名本身不提供可信签发时间，客户端无法加密地区分退役前产物和持有旧私钥后伪造的新产物，所以 `retired` 不是泄露处置手段。私钥疑似泄露或误签后必须使用 `revoked`，并接受下一版客户端会隔离该键全部插件、拒绝对应策略的结果。Windows 正式构建要求每个已声明用途至少保留一把 `active` 替代密钥。

当前仓库中的信任库故意为空；接入真实插件前，发布负责人必须注入组织的生产公钥。旧 `license.dat` 使用客户端内置 RSA 私钥解密，不能作为新的信任根，也不会复制进新客户端。

仅调试构建可通过 `SSDEV_ALLOW_UNSIGNED_PLUGINS=1` 临时加载未签名插件。Release 插件宿主会拒绝该选项。`SSDEV_PLUGIN_TRUST_STORE` 也只用于本地调试；正式客户端始终使用安装包内的 `plugin-trust.json`，启动环境不能替换发布信任根。
