# ADR-0001：Tauri 与 Rust WebPlus 目标架构

- 状态：已接受
- 日期：2026-08-11

## 背景

旧 ssdev-desktop 使用 Electron 加载远程业务页面，并通过 Electron IPC 提供窗口能力。旧 WebPlus 通过 localhost HTTP 让普通浏览器调用本地 DLL、OCX、EXE 和 BAT。迁移到 Tauri 后，应用内页面不再需要通过开放端口绕回本机能力。

## 决策

1. Tauri 负责可信桌面壳、窗口、托盘、配置、更新和远程页面生命周期。
2. Rust controller 负责服务路由、策略、超时和插件宿主监督。
3. 第三方原生组件只在独立的 `plugin-host` 进程中加载。
4. 每种宿主架构单独构建：`i686-pc-windows-msvc` 与 `x86_64-pc-windows-msvc`。
5. Tauri 到 controller 使用内部 command；controller 到 Windows 宿主使用随机命名、仅本机、双方 PID 认证的专用双向命名管道，管道内承载带 4 字节长度前缀的 JSON 帧。非 Windows 开发回归保留 stdin/stdout 传输。
6. 旧 HTTP API 后续实现为 controller 的可选 adapter，默认关闭。
7. 远程业务来源使用运行时 Tauri ACL 与 Rust 命令内授权两道边界；ACL 只从发布方签名策略与当前配置的交集生成，不为 SSO 导航来源授权。
8. 正式版配置和插件只使用操作系统/Tauri 标准应用目录；路径环境变量仅供 Debug 测试，不能把生产客户端引向任意目录。
9. 业务 Web Bridge 和 controller/plugin-host 私有 IPC 使用两个独立版本域。公开桥接版本由 SDK 契约治理，宿主版本只治理内部帧；任一版本升级不得无理由迫使另一层同步升级。

## 安全边界

- 远程 WebView 不直接获得 Shell、文件系统、进程启动或任意窗口创建权限。
- `plugin_invoke` 必须先通过精确来源的 Tauri ACL，再校验窗口标签、当前来源、签名策略、服务路由、参数大小和方法策略。
- 插件包必须使用服务端私钥签名；客户端只保存公钥。
- 插件宿主纳入 Windows Job Object，父进程退出时必须被回收。
- Windows 宿主标准输出、标准错误和协议通道必须分离；连接后先完成有界 Health 握手，第三方 DLL 输出不得污染控制帧或回传给业务页。
- 插件崩溃、超时和协议损坏不得影响 Tauri 主进程。
- controller 对所有入口统一实施最多 8 个在途插件调用的无队列准入；容量饱和时必须在进入路由和插件宿主前返回 `ResCode = -32001`，避免远程页面用并发大请求建立无界内存队列。
- 请求通过准入后必须由独立监督任务执行到响应或受控超时；页面导航、WebView 销毁或调用方 Future 被丢弃只能脱离等待，不能取消、重试或破坏潜在非幂等的原生调用及管道响应关联。
- 兼容 `invokePlugin` 不承诺结果找回；非幂等业务应使用可选持久操作 ID。持久调用必须先同步记录域分离请求哈希再进入 controller，整个“接纳、执行、完成标记”由独立监督任务持有；同 ID 同请求只执行一次，换请求硬失败。崩溃窗口不能伪装成 exactly-once，必须恢复为结果未知并禁止自动重放，账本不得持久化业务参数或响应。
- 所有正常退出和重启请求必须先原子关闭新调用准入，再有界排空已开始的调用并关闭宿主；排空期间尚未开始的竞态请求以 `ResCode = -32002` 明确拒绝。达到退出期限后由 Job Object 做最终进程回收。
- 同一插件/目录/架构的串行执行槽等待不得绕开方法超时；宿主就绪后，等待执行槽和实际 IPC 调用共享同一个截止时间。截止前未取得槽位的请求以 `ResCode = -32003` 返回并保证未执行，不得淘汰仍在为其他请求工作的健康宿主。
- 单插件安装和热更新必须使用按插件隔离的维护门、生命周期锁和维护代次：先推进目标插件代次，再等待它的写锁，以便目标插件排空期间的新请求立即以 `ResCode = -32010` 返回，而无关插件继续调用且宿主不被停止。候选宿主预检应在签名暂存目录同时持有全局与目标插件的生命周期读锁完成，耗时的宿主启动不能占用维护写锁；只有目标插件的原子目录/路由切换进入短维护窗口。完整重新扫描、退出和本体更新使用全局生命周期门，并与所有按插件维护互斥。

## 兼容门槛

正式切换前必须同时满足：

1. 旧请求样例可以无损反序列化，新响应字段与旧接口完全一致。
2. 每个在用插件至少有一组黄金输入输出回归用例。
3. 32 位 DLL、COM/OCX、EXE/BAT 四条路径都通过真实 Windows 设备测试。
4. 登录、打印、下载、上传、多窗口、悬浮窗、截图和缓存更新完成端到端回归。
5. Tauri 远程 capability 不包含通配 Origin，不开放通用 Shell/FS 权限。
6. HTTP 兼容网关关闭时，Tauri 内全部业务仍可正常工作。
7. 插件安装、升级不仅在普通错误时回滚，还必须用持久事务标记保证进程崩溃或断电后可确定、幂等地恢复；旧 Electron 配置可以一次性迁移。
8. 候选插件只能在对应 x86/x64 隔离宿主完成认证 Health 预检后提交；安装预检不得执行业务方法，真实 ABI 与硬件副作用由独立黄金矩阵覆盖。
9. 同一插件目录与 CPU 架构的宿主创建必须单航班执行；并发首调共享一个初始化槽，禁止重复加载厂商组件或并发争抢同一设备。启动或传输失败后保留 1 秒冷却状态，冷却内不得形成重启风暴，期满后才允许一次新初始化。
10. 调用方取消等待后，已接纳调用仍必须保有准入许可和生命周期读锁直到结束；诊断应只记录脱离次数，不记录请求或响应内容。
11. 托盘退出、操作系统退出和应用重启必须汇入同一个幂等排空入口；更新安装在宿主关闭后失败时必须恢复调用准入，不能让仍在运行的客户端永久停机。
12. 对每个“可以安全重试”的错误都必须证明请求没有进入原生组件：容量拒绝为 `-32001`、退出准入拒绝为 `-32002`、串行执行槽截止为 `-32003`、维护代次拒绝为 `-32010`；其他超时和宿主错误一律视为执行状态未知。四个代码必须由 Rust 公共响应常量、共享 Web Bridge 契约和 TypeScript SDK 分类器交叉校验，并由 controller 独占发行；宿主或厂商组件返回同码时必须改写为一般宿主失败，不能伪造“保证未执行”。SDK 只提供执行语义与重试建议分类，不自动循环重试，且退出排空只能在客户端重启后重试。
13. 全局和按插件维护状态都必须由 RAII 守卫持有；维护 Future 被取消或提前返回时也必须恢复对应范围的运行状态。同一插件的并发维护必须串行，不同插件不得共享排空锁；全局维护必须等待所有按插件维护退出。
14. 持久操作 ID 必须是安全随机 UUID v4，并绑定来源、路由和完整请求哈希；完成结果可有界地只存内存，但已接纳/已完成防重放证据必须先落盘。账本不可用时只能显式禁用持久接口，不能降级为无账本执行。持久容量必须同时有全局和来源级上限，单一来源不能耗尽全部防重放证据空间；过期清理不得在每次业务调用上线性扫描完整账本。
15. 状态页和诊断包必须分别报告业务桥接版本与插件宿主协议版本；契约测试只能将业务 SDK 与桥接版本比较，不能再次引用宿主协议常量。
16. 候选插件必须在暂存目录通过隔离宿主预检后才允许激活；激活后仍须对目标目录二次验签并验证完整路由，以抵御预检与切换之间的文件变化。预检失败不得触碰现有插件目录或活动路由。
17. 业务侧不能仅凭 JavaScript 方法存在就判断持久调用可用。系统声明必须提供独立版本的能力对象，区分协议支持、账本启动状态和当前准入状态；容量及保留边界必须直接来自实现常量并由 Rust/SDK 共享契约测试锁定。旧客户端没有能力对象时只允许继续基础桥接，不能被误判为已具备持久防重保障。
18. 旧插件发布必须采用可重复的两阶段流水线：离线准备阶段生成规范化版本元数据、完整文件清单和待签字节，生产私钥只在外部 KMS/HSM/受控 CI 中签名；封包阶段必须重算材料、用发布公钥验签并生成确定性归档。黄金矩阵脚手架必须默认处于不可执行草稿态，未显式完成脱敏输入和预期输出前不得接触真实硬件。
19. 来源策略、受控进程策略和插件目录的 detached 签名必须共用同一个封套类型和发布工具；准备阶段先使用运行时同源解析器完成语义校验，再产生带域分隔的待签请求。导入签名时必须重算文档与审核摘要并强制精确密钥用途，不能为不同文档复制易漂移的人工签名脚本。
20. 插件仓库目录中的身份、版本、大小和摘要不得人工录入；发布工具必须先按客户端安装路径验证每个本地包的内部签名，从签名元数据提取身份/版本，在验证前后复算包摘要以检测变化，并按稳定顺序编码目录。目录签名与包签名继续使用不同用途密钥。
21. schema 2 信任密钥必须具有兼容默认值为 `active` 的显式生命周期：`active` 可进入官方签发并被运行时验证，`retired` 禁止官方新签发但为计划轮换继续验证有效签名，`revoked` 对所有产物失败。所有制作新插件、策略、目录及 Windows 正式发布的路径必须要求 active 密钥；生产信任库在退役或吊销旧键之前，必须为对应已声明用途加入至少一把 active 替代键。由于普通 Ed25519 签名不能证明签发时间，retired 不得作为私钥泄露处置；泄露必须 revoked，并同步迁移或重签受影响产物。
22. Windows 正式 bundle 必须携带 schema 2 发布溯源元数据，并由签名全产物清单覆盖。元数据固定绑定 Git 提交及脏状态、构建关键锁文件与配置摘要和工具版本；正式 Authenticode 发布拒绝脏源码和合成版本。候选包验收必须在对应源码检出中重新计算这些值，历史上一生产包只做结构和独立签名链验证。
23. SSO 是独立于业务来源兼容策略的敏感传输边界：登录请求始终使用系统信任的 HTTPS、禁止所有重定向并限制参数与响应大小；签名 `allowInsecureHttp` 不能授权明文 SSO。同一实例只允许一个 SSO 请求，避免并发身份响应乱序打开窗口；控制台只能看到固定状态码。SSO 导航来源只具备导航能力，不注册应用命令 ACL。现有查询参数令牌契约必须在服务端迁移为一次性短码或安全 Cookie，迁移前禁止代理和服务端记录查询参数。
24. 正式硬件矩阵不能只绑定一个可变插件目录。运行器必须接收已通过联合离线审批的发布集合规范，并在接触硬件前将现场根目录中的每个插件重新确定性封包；身份、版本、active 签名 keyId、数量、联合覆盖和逐包 SHA-256 均须与发布集合一致。机器证据使用独立 schema 2 绑定规范摘要与稳定包集合摘要，旧证据不得人工补字段升级。
25. 多插件发布集合从审批产物进入硬件环境时不能依赖人工逐包解压。标准工具只物化到尚不存在的新根目录，复用客户端安全解包和事务激活路径，并在完成后重新执行发布集合与逐包确定性摘要检查；普通失败删除半成品，进程崩溃留下未完成标记，所有矩阵检查和实机运行必须拒绝带标记目录。该工具不直接替换正在运行的生产插件根，运行期多插件切换仍须经过独立维护与灰度流程。
26. “来源策略签名有效”和“插件成功加载”不能分别作为交付就绪证明。控制器必须在每条活动服务路由中保存共享的完整插件清单快照；部署自检在插件安装锁内重新发现磁盘清单，与该快照精确比较身份/版本、路径及全部服务/方法契约，而不是只比较服务数量，并把当前业务来源与全部公开 `serviceId + method/alias` 做覆盖分析：每个当前来源至少覆盖一项已安装能力，每条公开调用路由至少被一个当前来源覆盖。检查只返回计数或通用漂移状态，不输出来源或调用路由名称，也不以通配授权修复漏项。自动状态刷新不得隐式启动插件宿主，并必须把结果标为快速检查；无阻塞的快速结果只能表示 `ready`，不能被界面或导出消费者解释为正式可交付。报告必须独立声明平台是否支持深度检查，并且只有 Windows 深度检查实际完成且无阻塞时才声明 `deliveryReady`。用户触发的 Windows 深度自检与现场记录导出应为当前每个有效插件的实际架构重新完成候选宿主 Health 预检，失败直接阻塞交付，但不得执行业务方法或替换活动路由。磁盘变化不能自动热加载；显式完整重扫必须先重新验签并为每个有效清单完成候选宿主预检，再进入全局维护替换路由。
27. 项目部署包不是若干独立插件安装的便捷循环，而是配置、签名插件、本地映射和联合路由的一个交付事务。所有候选先完成签名、授权覆盖、路由和宿主预检；确认后在全局维护窗口内写入持久项目事务、切换全部目录、一次替换联合路由并最后替换配置。项目级原子提交点之前的失败或崩溃整体回滚，提交点之后整体完成清理；运行期不能在不刷新内存配置的情况下恢复未提交配置，必须由下次启动完成。
28. 项目部署包必须具有独立于插件、目录和策略的 `project-bundle` 发布用途。签名覆盖整个 `.ssdev-project` 原始文件摘要，使配置、本地映射、内部包和容器重排都不可替换；正式客户端按固定同目录旁签命名失败关闭，只有显式 Debug 未签名模式可以绕过。签发继续复用无私钥的统一外部签名工具，生产 Windows 信任库必须为该用途保留 active 发布键。
29. 插件删除不是裸目录递归操作。签名插件卸载和本地映射删除必须复用更新所用的持久激活事务，并只进入目标插件的维护窗口：先暂存旧目录，再验证删除后的联合清单，原子移除精确路由后才提交。提交前失败或崩溃恢复原目录和路由，提交后只完成备份清理；无关插件不能因单插件删除而排空或重启。业务 WebView 不具备删除权限。
30. 签名插件必须在签名覆盖的 `plugin.json` 中声明已经验证的 Desktop SemVer requirement。运行时启动、手工安装、仓库安装和项目包导入都必须以实际 Desktop 版本失败关闭；仓库只选择最高兼容插件版本，并把目录范围与包内范围精确绑定。为迁移诊断可解析缺少范围的旧元数据，但正式目录生成和统一签发必须拒绝它。应用本体检查更新时应报告目标版本的插件阻塞项，确认安装时还必须在插件安装锁内重新发现并复核，禁止检查后插件集合变化造成不兼容升级。
31. 项目包预检必须产生与实际导入一致的变更计划，而不是只展示候选清单。计划区分新增、升级、同版本修复、本地映射替换和未声明现有组件保留，不得暗示隐式删除；配置部分必须复用普通配置导入的统一差异模型，在受限本地控制窗口展示目标入口/环境以及来源、进程、快捷键和桌面行为变化，不能只返回“配置更新”。这些值不得进入结构化日志。确认标识使用域分隔摘要绑定项目包原始摘要、Desktop 版本、当前已保存配置、签名插件完整签名载荷和本地映射确定性包；导入命令必须在插件安装锁内重建全部输入并精确匹配该标识后才能开始事务，预检后任何相关状态漂移都要求重新确认。
32. 项目包导出不是不经验证的文件归档。配置机必须先确定性封装当前组件，再从即将写入项目包的精确候选重新解包，在插件安装锁内复用联合路由和来源授权覆盖规则，要求候选声明服务与控制器活动服务对账，并执行无业务副作用的候选宿主预检后才写出草稿；容器复制期间重新核对每个组件的大小与 SHA-256，成功后公开整个项目包摘要供外部签名请求核对。空项目保持可导出。更新端点、诊断组件、目标网络和真实原生方法结果属于机器特定验收，不进入可移植导出门禁。
33. 插件仓库更新不能把“检查时看到的版本”和“安装时重新解析出的同名版本”视为同一授权。检查结果必须产生域分隔确认标识，绑定精确目录条目、目录签名 keyId、Desktop 版本和目标插件当前签名载荷；安装命令只接受精确版本及对应标识，在插件安装锁内重新获取验签目录并复算本机基线，下载完成进入原子激活时再次复核。目录条目、签名身份或目标插件状态漂移时必须要求用户重新检查，不能继续下载或覆盖当前插件。
34. 应用本体更新的全局 pending 对象不能作为用户确认的隐式身份。检查结果必须用域分隔摘要绑定目标更新的版本、平台、下载 URL、Minisign 签名和用户看到的说明，以及当前全部签名插件载荷和本地映射确定性内容；安装命令接收该标识并在插件安装锁内精确复核 pending 与完整能力集合。开始新检查先清除旧 pending；包流式验签完成后、停止新调用和宿主前再次复核签名插件及本地映射，任一漂移都不得进入安装阶段。
35. 插件仓库必须区分“未收录历史版本”和“发布方明确撤回精确版本”。撤回记录与安装条目由同一短期目录签名覆盖，只接受固定原因码并按 `pluginId + SemVer` 唯一；同一版本不能同时可安装和撤回。客户端不得解析或安装撤回版本，检查到当前已安装版本撤回时应高优先级提示升级或卸载，但一次在线检查不能直接终止硬件调用或替代离线信任策略；签名密钥泄露仍必须通过信任库 `revoked` 强制隔离该键全部产物。
36. 普通桌面配置导入不能把文件选择同时视为覆盖确认。预检必须先完成配置语义和来源策略授权，展示会影响业务入口、来源、环境、受控进程、快捷键及启动行为的摘要，并生成域分隔确认标识绑定候选配置与当前已保存配置。确认命令必须在插件安装锁内重新读取候选文件、重新授权并复算标识；候选或当前状态漂移时要求重新预检。语义相同的配置属于无操作，不能仅为重新导入而关闭业务窗口或重写系统启动状态。
37. Windows Release 不得把终端输出或日志文件作为启动失败的唯一反馈。Tauri 初始化前后必须维护固定、无敏感内容的启动阶段；构建失败和启动期主线程 panic 通过原生系统对话框显示稳定错误码、处理建议及日志目录。控制窗口创建成功也不等于前端可用，页面必须在有界时间内通过本地控制命令证明已到达 Rust IPC；超时只提示一次并记录脱敏标记。就绪与超时必须由一个互斥状态机裁决，成功到达 IPC 后还要在固定标记中保留原故障并写入恢复时间和应用版本，不能留下无法区分当前故障与历史故障的未解决文件。业务 URL、原始异常、配置内容和组件绝对路径不得进入启动事件或标记文件。
38. 本地选择 `.ssdev-plugin` 文件不能同时视为安装确认。控制台必须先在只读阶段重新解包、验签、检查 Desktop 兼容范围、防降级、联合路由和当前活动路由一致性，并在真实候选 x86/x64 宿主完成无业务副作用的 Health 预检；预览只展示插件身份、版本变化、服务/方法和预检计数，不返回本机路径或签名密钥。确认标识以独立域分隔摘要绑定候选插件的规范签名载荷、目标插件当前签名状态和 Desktop 版本。安装命令必须在安装锁内重新准备同一文件并复算标识，进入原子激活前再次复核目标插件基线；候选或当前状态漂移时要求重新预检，不能继续覆盖。
39. 签名插件仓库必须支持无需预知插件 ID 的全量发现，而不能把目录能力限制为已安装插件更新。全量检查按稳定 ID 合并仓库条目与已安装签名插件，每个 ID 只选择当前 Desktop 的最高兼容未撤回版本，并同时报告仓库最高版本、撤回和兼容受限状态；精确 ID 查询继续保留。目录浏览不得下载或激活插件。与本地映射同 ID 或同名目标目录无效的候选只能返回稳定阻塞分类且不生成确认标识，一个阻塞项不能使其他已验证条目消失；业务 WebView 仍不具备目录查询或安装权限。
40. 插件发现中的“不可调用”不能等同于“磁盘目标不存在”。扫描器必须在验签、兼容和本地映射定义校验之前保留规范化插件身份；仓库检查、本地包预检和最终激活都必须使用该磁盘身份集合拒绝同 ID 映射。身份冲突按 ASCII 大小写不敏感比较，以匹配 Windows 文件系统和发布集合门禁。损坏或已隔离映射不能因为未进入活动清单而获得覆盖它的签名插件安装计划。
41. 已成功提交但现场表现异常的插件版本需要显式止损路径，不能把自动失败回滚误当成运维回退。只有内置控制台对已安装签名插件的精确仓库查询可以生成回退计划；目标必须低于当前版本、仍可安装、未撤回并匹配当前 Desktop，历史列表有界且不进入全量浏览。每个目标继续绑定目录签名身份、精确条目、Desktop 和当前插件载荷，确认后复用下载二次验签、候选宿主预检、按插件维护及持久原子激活。普通本地包和项目导入继续防降级；程序回退不宣称恢复设备状态或业务数据。
42. 签名有效不代表插件适合进入当前项目的活动路由。本地签名包预检及确认、仓库安装/更新/回退和管理员显式重扫，都必须在启动候选宿主或进入维护窗口前，以当前已保存配置和已验签来源策略检查安装后的完整签名插件集合；每条规范方法名及 alias 至少被一个当前业务来源授权，否则以脱敏计数失败关闭。单包顺序安装不能要求每个业务来源都覆盖每个插件，否则多项目或按需能力会被错误阻塞。开发中的本地映射保留工作台调试入口；项目包导出/导入和部署自检继续对签名插件与本地映射执行每来源、每路由的严格联合覆盖。
43. 来源与插件是同一可调用边界，不能只在插件变化时检查。普通配置保存和导入若改变业务来源集合，必须在插件安装锁内读取控制器当前活动的完整、去重清单，并要求候选配置继续让每条签名插件规范方法及 alias 至少被一个来源授权；失败只报告脱敏计数，且不能关闭业务窗口、改快捷键、改开机启动或写配置。来源集合未变化时不因历史部署问题阻断无关桌面设置。本地映射继续允许现场调试；需要同时替换来源和能力时使用已经联合预检并原子提交配置与组件的项目部署包，不能依赖普通配置与逐包安装的顺序碰巧成功。
44. TypeScript 接口不能证明运行时注入值满足桥接契约。SDK 建立连接时必须先验证基础系统声明和当前已知能力 schema，再比较公开桥接协议；损坏字段或互相矛盾的能力状态以稳定、无敏感内容的原因失败，不能泄漏为普通 `TypeError` 或触发 HTTP 回退。能力 schema 独立于桥接协议向前演进：更高的未知 schema 可以继续使用已经协商的基础桥接并保留只读声明，但所有依赖该能力对象的可选功能都视为不可用，直到 SDK 显式支持该 schema；不能因可选 JavaScript 方法恰好存在而猜测兼容。
45. 原生映射表单中的未提交声明是现场实施状态，不能被新建、切换、导入或关闭窗口静默覆盖。控制台必须用规范化持久声明跟踪草稿基线，并在替换编辑器内容前明确确认；调试用例的独立持久化只能更新基线中的用例部分，不能清除其他 ABI 字段的脏状态。项目包命令成功后必须重建工作台以读取新磁盘映射，命令失败时不得丢弃原草稿；这项界面同步不能被误当成项目事务提交条件。
46. 未签名本地映射包不能把文件选择视为执行原生代码的授权。第一阶段只允许有界解包和声明、文件、架构、路由结构校验，不能启动候选宿主；预览只显示脱敏能力范围并明确其不证明发布者身份。确认标识必须绑定原始包摘要、Desktop 版本和目标映射的确定性当前内容，确认命令重新打开文件、复建候选并复算标识；之后才允许在隔离宿主 Health 预检和按插件维护窗口中原子激活。文件或目标状态漂移、签名插件冲突、隔离目标或磁盘清单与活动路由不一致时必须失败并要求重新预检。
47. 本地映射的目录边界不能替代内容身份。schema 2 映射必须包含由运行声明精确派生的完整性清单，固定 API、元数据、入口组件和依赖；发现与每次宿主启动都在加载原生代码前逐文件验证。控制器路由保留已批准完整性文档摘要并通过私有宿主参数下发，阻止运行期文件或清单变化在宿主重启后静默生效。旧 schema 1 只允许在启动事务恢复后一次性生成清单并提升版本；schema 2 缺失或无效时失败关闭。该清单只提供本机运行态固定，不替代组织发布者签名。
48. 宿主进程存活不能作为原生能力可运行的证明。控制器必须把目标架构作为私有宿主启动参数，宿主先核对自身编译位数并只接受该架构声明的服务，再在返回 Health 前由专用原生线程完成无业务调用的初始化：DLL 及依赖实际加载并解析全部声明导出，COM/OCX 初始化 STA、实例化类并解析方法与属性，EXE/BAT 只验证受控普通文件且不得执行。DLL 主模块在宿主生命周期内保持加载，避免首个业务请求重新选择磁盘文件。位数、依赖、导出、注册或静态 ABI 声明失败必须在候选激活、深度自检和宿主重启时失败关闭；参数值、真实返回和硬件副作用仍由黄金矩阵证明。
49. EXE/BAT 的启动时文件选择必须继续受宿主二次信任校验约束，不能只依赖 Health 前的一次路径检查。签名宿主把已验证发布清单的逐文件 SHA-256、本地映射宿主把已固定完整性文档的逐文件 SHA-256 传入原生适配器；预检必须按入口逐项匹配，并在 Windows 宿主生命周期持有不共享写入和删除的文件句柄。每次创建进程前仍从目标路径重新读取和散列，摘要漂移、缺失或不可重新打开都在执行前失败关闭。该保护不执行入口，也不替代黄金矩阵对进程行为的验证。
50. 聚合宿主启动计数不足以定位多插件、多位数项目中的现场故障。controller 必须从当前活动路由生成按插件与架构去重的只读健康快照，区分尚未启动的按需待机、运行中、短期重启退避和退避结束后的等待重试，并在路由生命周期内保留累计失败次数及最后一个稳定诊断码。等待重试只有真实启动成功或路由替换才清除，不能仅因退避计时结束而伪装成初始待机。快照不得为检查状态而启动宿主，也不得包含目录、原生错误原文、请求或响应；详细快照只提供给本地控制窗口，脱敏诊断包继续使用聚合计数。
51. 宿主失败后的人工恢复不能借用一次真实业务调用，因为打印、写卡等方法可能具有不可逆副作用。仅限本地控制窗口按活动路由提交精确插件 ID 与 x86/x64，controller 同时持有全局和目标插件生命周期读锁，并只启动或复用该运行宿主完成原生初始化与 Health；不得构造业务 Invoke、启动 EXE/BAT、修改插件文件或替换路由。操作员恢复可绕过当前一次短退避，但全局重载、目标插件维护或退出期间必须失败关闭；错误只返回稳定诊断码，业务 WebView 不获得对应 ACL。
52. 把所有原生 Health 失败压缩为 `native-host-error` 会迫使现场人员依赖厂商原文或猜测。原生适配器应从结构化错误枚举产生固定、路径无关的内部类别，宿主只转发类别而丢弃消息；controller 必须再次以白名单映射为公开稳定码，未知代码一律降级为通用宿主错误。只有本地控制台可根据稳定码展示 DLL 位数/依赖/导出、COM 注册、进程文件完整性或安装修复建议；业务页面、诊断包和日志不得获得原始路径、类名、导出名、注册表错误或厂商文本。
53. 候选预检错误不能因为只展示在本地控制台就重新暴露内部 `ControllerError`。controller 必须为安装、更新、本地映射和部署自检返回只含插件 ID、可确定的目标架构与白名单稳定码的结构化失败；尚未进入宿主的生命周期失败不虚构架构。所有面向操作员的预检提示和深度自检建议只能由这些字段生成，禁止附加原始错误、路径或厂商文本；Windows x86/x64 真实宿主回归必须验证缺失组件仍保留正确插件、架构和稳定类别。
54. 运行时 API 兼容检查不能只依赖进程内活动清单，否则完全退出期间直接替换一个仍可验签的同 ID 包会在下次启动丢失比较基线。客户端必须在标准本地数据目录原子保存有界的已接受签名契约，只记录插件 ID、版本、验证后的服务声明和安装/墓碑状态；首次启用采用当前已验签安装，此后同 ID 离线破坏性变化在路由加载前隔离。未解释的缺失保留契约墓碑，普通安装、项目导入或重扫不能顺带清除，只有对应显式卸载提交才退休。基线内容无效、超限或符号链接时失败关闭，日志只记录稳定码和聚合数量。
55. 插件目录事务与契约基线不能依赖两个无关联的先后写入。安装、仓库更新/回退、卸载、项目导入和完整重扫必须在自身持久提交点之前先写有界的下一契约集；普通错误以 RAII 清理，提交后再提升为主基线。启动时必须先恢复插件/项目目录事务，再将完整磁盘签名插件集与旧/下一契约集精确比较，只允许确定性撤销或完成；歧义状态失败关闭。准备写入失败必须阻止插件提交；提交后的提升失败保留恢复记录并累计稳定诊断，不能谎报插件已回滚。墓碑状态必须进入契约文件，保证无关变更和崩溃恢复都不会意外退休缺失身份。
56. 生产硬件矩阵不能使用脚本临时编译的 Debug 插件宿主来替代候选安装包中的 Release/签名宿主。矩阵运行器必须显式接收本次构建待交付的 x86/x64 文件并把 SHA-256 写入证据；Windows 包验收必须从实际安装目录记录插件信任库及同一对宿主摘要，生产策略还要绑定最终产物清单。最终 Go/No-Go 只有在批准输入和两份独立 QA 证据逐字节一致时才能通过，避免插件和硬件用例正确但实际随包信任根、宿主或候选包从未被测试。
57. 生产黄金矩阵包装器不能只依赖跨平台文本断言证明可执行。默认 Windows 原生门禁必须生成一个 x86 和一个 x64 最小插件，使用明确限定为 `ci.*` 身份和固定 CI keyId 的公开 RFC 8032 测试向量完成两阶段签名，通过正式发布集合检查及物化后，把当前门禁已构建的 Release 双架构宿主作为精确输入运行同一包装器；只有两个方法实际返回精确黄金结果，且 schema、覆盖计数、clean commit 和两个宿主摘要全部匹配时门禁才通过。该公开测试种子不得接受任意 keyId 或生产插件身份，也不能成为生产签名文档或交付信任库的一部分。CI Release 宿主仍未经过生产 Authenticode，不能替代候选安装包构建留下的精确已签名文件或最终 Go/No-Go 身份对账。
58. 内网 HTTP 兼容不能用迁移审计中的无条件阻断覆盖已经签名批准的来源策略。正式迁移审计必须先以活动发布密钥验签候选来源策略，再复用运行时授权规则逐项检查实际配置；只有被该精确策略覆盖的 HTTP 来源可以从关键阻断降为已授权信息，其他 HTTP 或业务来源策略不匹配仍失败关闭。迁移证据 schema 3、Windows 包证据 schema 7 和当前生产切换策略必须绑定同一来源策略 SHA-256，并记录 HTTP 总数与已授权数；摘要漂移或授权覆盖不完整必须阻断最终 Go/No-Go。
59. 真实项目试点不能用口头确认或零散共享目录代替可移交的输入基线。只读材料预检必须固定生产原生组件、黄金用例、业务产物/HAR、签名来源策略、插件发布集合、组织公开信任材料、上一 Windows 版本和实机计划等必需类别；旧快捷键、受控进程和外部本机 HTTP 调用方只有引用明确审批时才能声明不适用。schema 2 manifest 还必须把正式迁移审计的配置、插件、快捷键、业务资源、HAR 和签名策略角色精确绑定到相应类别。预检拒绝绝对/穿越路径、符号链接、特殊文件、无界目录和公开信任类别中的明显私钥材料，报告只保留类别、数量、角色摘要、集合摘要、审批引用摘要和稳定阻断码。接收方必须能严格加载报告并对同一 manifest 与材料目录重算逐字段身份，任何报告、清单、角色或材料漂移都失败。材料齐全始终不等于语义、签名、硬件、升级或生产切换通过，报告必须显式要求后续验证，不能进入 Go/No-Go 证据链替代任一独立执行环境。
60. 正式迁移审计不能在已复验试点移交之后重新接受人工路径选择。正式命令只接收材料根、manifest 和预检报告三件套，要求报告完整，并从已绑定角色派生全部审计输入及签名来源策略；手工输入只允许产生无正式证据的探索报告。审计结束前必须再次复验材料、manifest、报告、源码和策略。schema 4 完整报告公开无路径的材料集合与角色摘要，schema 3 迁移证据把材料集合摘要传入当前生产策略的精确期望值；集合不一致必须阻断 Go/No-Go，覆盖计数下限不能替代内容身份绑定。
61. Windows 升级通过不能只证明候选包可以覆盖任意一个版本号更低的安装。试点材料必须提供上一生产版本的完整已验签 bundle，而不是零散安装器；schema 7 Windows 包证据必须记录其版本、`release.json` SHA-256 和签名全产物清单 SHA-256。当前生产策略逐项指定这三个值及候选产物清单，最终 Go/No-Go 对任一不一致失败关闭。CI 合成 `0.0.1` 只证明升级脚本可执行，不能替代真实上一生产版本的身份和现场演练。
62. 生产切换策略不能依赖实施人员从多个报告和目录手工复制版本及摘要。标准策略生成器必须从当前 clean 源码、已复验试点 manifest/报告/材料、候选与上一生产完整 bundle、批准发布集合、唯一黄金矩阵和 active 签名来源策略确定性派生所有项目事实；发布集合引用的每个包必须位于试点批准的包目录。唯一允许人工提供的是证据时效、八类迁移覆盖下限和四个互异职责签名人。输出必须在所有输入边界之外且不可覆盖，写入前再次复验源码、材料、bundle 和人工批准文件；任一漂移、错版本、无效签名或候选来源不一致都不得产生策略。
63. keyId 只标识策略预期的职责，不能单独充当信任根身份。schema 7 生产策略必须绑定来自试点 `organization-public-trust` 材料的 QA 证据信任库原始字节 SHA-256，并在生成时证明三个互异 QA keyId 都是 active `cutover-evidence` 密钥；Go/No-Go 使用另一份库即稳定 `NO-GO`。最终 schema 3 决策还必须携带策略已绑定的插件/发布信任库摘要作为 `approvalTrustStoreSha256`，统一签名工具在 `prepare`、`finalize` 和 `verify` 三阶段都核对实际库原始字节，同名 keyId 的替代公钥库不得签发或复验 GO。最终审批 keyId 必须在生成策略时已经是该发布库中的 active `cutover-decision` 密钥。
64. 自动生成和不可覆盖只能证明策略来源过程受约束，不能证明判定时读取的策略仍是组织批准版本。schema 7 策略必须在任何证据判定前由既定最终审批职责使用获准发布信任库签名；不增加第五个职责，但使用 `SSDEV-CUTOVER-POLICY\0` 独立域，禁止策略封套与最终 `SSDEV-CUTOVER-DECISION\0` GO 封套互换。`decide` 必须先验证策略 keyId、用途、签名和信任库原始字节身份，再验证三份 QA 证据，并在 schema 3 决策中记录策略及其封套 SHA-256 和实际两份信任库摘要。未签名、替换、旧 schema 2 决策或同名 keyId 替代信任库都不能进入最终签发。
65. 创建业务 WebView 只能证明桌面 API 接受了窗口请求，不能证明目标页面、网络、证书和桥接脚本可用。每次导航到已配置业务来源时，注入脚本必须在 DOM 就绪后通过只授予业务窗口的内部命令到达 Rust IPC；30 秒内没有信号即进入可恢复的超时状态并显示稳定错误码。导航到受信任 SSO 等非业务来源只标记为导航中，不启动超时；返回业务来源后重新计时。首页、部署自检和诊断包只公开聚合状态与累计超时/恢复计数，不记录 URL 或窗口身份；Windows 深度交付就绪必须至少包含一个真实业务页面握手，快速日常检查在未启动窗口时不得阻断。
66. 运行时能显示业务页面已就绪但生产 Go/No-Go 不读取该事实，仍可能让只启动过控制台的候选包进入切换。schema 7 Windows 包证据允许普通 CI 显式保留空部署记录，但生产判定必须要求一份由同版本 Windows 客户端在一小时内导出的 schema 1 深度检查；工具严格核对 13 个固定检查项、计数、`deliveryReady` 及 `business-frontend: pass`，并把原始文件 SHA-256 和生成时间纳入 Windows QA 签名摘要。记录缺失稳定阻断为 `windows-business-frontend-not-verified`；版本、平台、完整性或业务握手不符在证据生成前失败，不能用手工布尔值替代。
67. 候选包能够从上一版本升级并卸载，不等于现场已经具备恢复路径。Windows 包门禁必须在候选验证后卸载候选，使用策略指定的同一上一生产 bundle 重新安装，复核上一版本 Authenticode、安装布局、未知配置字段和实际启动，再完成最终卸载。schema 7 必须把 `rollbackVerified` 与 `upgradeVerified` 分开记录；没有上一版本、跳过启动或任一步失败都不能生成回退通过，最终 Go/No-Go 以 `windows-rollback-not-verified` 阻断。该结论只覆盖客户端安装层，不宣称逆转外部硬件调用或业务系统中的非幂等副作用。
68. WebView2 `OfflineInstaller` 与 `DownloadBootstrapper` 是安装期运行时供给方式，不是桌面数据或插件 ABI。真实上一生产版常为离线包，不能因为候选采用在线轻量包就失去升级与回退验收路径。Windows 门禁必须分别验证候选和上一 bundle 的签名 `package-profile.json`，保持桌面目标架构一致，同时允许显式声明不同 WebView2 模式；未声明上一模式时才沿用候选模式。默认 CI 对 x86/x64 都执行离线旧版到在线轻量候选的升级、配置保留、候选卸载、离线旧版回装和启动，证明轻量化不会牺牲恢复路径。
69. 包验收脚本在安装前验证过全产物清单，不代表写证据时待交付 bundle 仍保持原样。Windows 证据生成器必须在读取发布元数据前和写出证据前分别用规范 `artifacts.json` 重新扫描候选与上一版本完整文件集，同时继续比较清单及元数据原始摘要；安装器、updater、策略、宿主、SBOM 或其他受覆盖文件漂移时不得产生可签名证据。该复验不替代独立更新公钥对清单签名的验证，而是关闭测试结束到证据落盘之间的本地文件竞态。
70. 只在 `%APPDATA%` 放置未知配置字段，不能证明升级、候选卸载和上一版回装没有清理 `%LOCALAPPDATA%` 中的签名插件或本地映射。隔离账户的 Windows 包门禁必须在标准配置根、插件根和本地映射根创建运行时明确忽略的有界哨兵，并在上一版启动、候选升级与启动、候选卸载、上一版回装与启动以及最终卸载后逐字节复核。该哨兵只证明客户端数据目录保留，不替代真实插件黄金矩阵，也不能证明外部设备副作用可回退。
71. 脚本日志显示状态哨兵通过不足以让证据审批者或最终判定依赖该事实。schema 7 Windows 包证据必须新增 `applicationStatePreservationVerified`，统一外部签名摘要必须公开该值；它为真却没有 NSIS 与上一版本升级结果属于矛盾证据。生产 Go/No-Go 必须独立要求该字段，否则以 `windows-application-state-preservation-not-verified` 阻断，不能用 `rollbackVerified` 或上一版本成功启动代替。
72. 应用更新安装器交接前关闭业务窗口，会在签名包解包或系统安装程序启动失败时丢失仍可运行的用户工作区。二次复核后必须先通知本地控制台进入安装阶段，再停止 controller 与持久协调器的新调用并排空宿主；业务 WebView 保留到安装器成功接管后的进程退出或重启。交接失败必须同时恢复两层准入、保留原业务窗口并记录稳定事件 `app-update-install-handoff-failed`，不能要求用户重开窗口或重启旧客户端才能恢复工作。控制台还必须退出安装中状态并作废已消费的计划标识，要求重新检查后再尝试，不能让看似可用的按钮提交一个已不存在的 pending 更新。
73. 有界流式下载不能忽略进程崩溃留下的更新包临时文件，否则多次网络或进程故障可持续消耗本地磁盘。每次下载前必须验证固定更新临时根为非符号链接目录，只删除该根内由客户端固定前缀标识的普通文件；目录、符号链接和其他文件必须保留。当前下载继续使用自动删除的临时文件，普通错误由所有权析构清理，崩溃残留在下一次受控更新尝试前清除。
74. 本地控制窗口受信任不等于可以直接展示 updater、HTTP 或安装器原始错误；这些错误通常携带私有更新端点、下载 URL、临时路径或底层实现细节。运行时更新检查、下载、HTTP 状态、流中断和安装器交接必须映射为稳定错误码与处理方向，结构化日志只记录对应事件码、错误类别、可选 HTTP 状态和聚合计数。发布期离线产物验证工具可以保留面向受控构建人员的文件错误，但不得复用到桌面运行时反馈。
75. “前置条件已经检查”不能成为桌面主进程、插件宿主或原生适配器使用 `unwrap`、`expect`、`panic` 或 `unreachable` 的理由。业务配置、签名目录、插件状态和宿主可用性都可能因磁盘、并发或未来代码变化打破内部假设；生产路径必须返回显式错误、隔离失败组件或生成失败检查项。自动门禁扫描桌面、controller、插件宿主和原生适配器的非测试 Rust 源码，测试代码可以继续用硬断言表达 fixture 不变量。
76. 持久调用不能只用 RAII 递减活动计数后丢弃工作流 `JoinHandle`。依赖或运行时异常仍可能让内存状态和所有等待者永久停留在 `pending`，即使退出排空计数已经恢复。独立监督任务必须观察工作流终止并查询持久账本：尚未接纳时发布稳定可重试失败，已经接纳时发布 `indeterminate`，已有完成标记时发布 `completedWithoutResult`；账本复核失败必须保守发布 `indeterminate`。监督任务自身持有活动计数守卫，正常、panic、取消和复核失败都要解除退出等待，日志不得包含 JoinError、operation ID、来源、路由或调用数据。

## 不采用的方案

- 在 Tauri 主进程直接加载 DLL：第三方崩溃会带走整个桌面客户端。
- 继续以 localhost HTTP 作为内部总线：扩大攻击面且保留无意义的端口、CORS 和认证复杂度。
- 一次性替换全部 Go 行为后再测试：无法定位具体插件 ABI 差异。
