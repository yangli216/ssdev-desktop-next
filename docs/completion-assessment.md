# SSDEV Desktop Next 完成度评估

评估日期：2026-08-29

## 结论

项目已经具备进入“真实业务验收”的工程条件，但尚不能宣布生产切换完成。代码、自动测试和合成安装包门禁覆盖了 Tauri 桌面壳、无 HTTP 的 Web Bridge、x86/x64 隔离插件宿主、DLL/COM/OCX/EXE/BAT、签名插件生命周期、单包及多包发布集合与黄金矩阵联合离线检查、批准发布集合的一次性验收目录生成，以及现场插件目录到硬件证据的逐包摘要绑定、应用更新、配置迁移、SSO、多窗口、截图、诊断和供应链证据。剩余风险主要不是继续猜测实现，而是缺少生产插件、真实硬件、业务 HAR、生产签名体系和上一生产安装包等外部材料。

## 原平台能力覆盖判断

- 桌面壳主能力已覆盖：环境配置与迁移、托盘、单实例、多窗口、缩放/查找、开机启动、SSO、截图、缓存清理和诊断。
- WebPlus 主能力已覆盖：业务请求兼容、x86/x64 路由、DLL、COM/OCX、EXE/BAT、超时、背压、崩溃恢复和隔离宿主。
- 旧版任意 Shell 进程和 `eval` 快捷键没有原样迁移，而是替换为签名进程策略和声明式动作。这属于有意的安全收敛，不应作为缺失能力重新开放。
- 旧本机 HTTP 端口 `7711`、`45121` 不再是 Tauri 内部通信依赖。是否仍需独立兼容适配器，必须由代表性 HAR 和外部调用方清单决定。
- Win10/11 x64 与 x86 是正式目标；当前 Tauri/Rust/WebView2 组合不把 Win7 列为正式支持范围。

## DLL 映射可视化

内置控制台既展示通过当前信任库验签并重新发现成功的发布插件，也提供可写的本地原生映射工作台。发布插件提供以下只读拓扑：

`插件 ID/版本 → serviceId → x86/x64 与 mainType → mainClass（DLL 相对路径或 COM ProgID）→ 请求方法名 → 原生导出/成员名`

同时展示调用约定、字符集、服务/方法超时、缓存策略、依赖数、参数数和返回类型。绝对插件根目录不进入发布映射数据；隔离插件不进入可调用拓扑。

本地工作台可以选择 DLL/EXE/BAT、只读识别 PE 架构和命名导出，或按 x86/x64 注册视图搜索 COM/OCX 后选择 ProgID/CLSID；管理员可编辑服务、方法、参数、返回值、依赖、字符集和调用约定。保存时组件被复制到固定本地映射根目录，在正确位数的隔离宿主中预检，然后以持久事务原子热加载；普通失败和进程崩溃都会恢复旧目录和路由。工作台还提供同路由现场调用、耗时与结构化结果查看，可保存有界的合成输入并顺序回归 `ResCode`、`ReturnValue` 和关键输出字段，以及导出类型化 Web Bridge 客户端和包含组件/用例的 `.ssdev-mapping`。稳定映射可导出仅含 API 与引用组件的最小发布源，并在其目录外生成仍为草稿的正式矩阵种子；签名工具会强校验路由、完整输入和全方法覆盖，正式运行器即使遇到被误改为非草稿的遗留占位符或未解除的精确响应复核标记，也会在启动宿主前失败，同时避免现场用例进入签名插件。COM 注册发现只读元数据且不实例化未知组件；复杂结构体、回调或厂商自定义 ABI 仍需要专用 Rust 适配器。

## 更新机制

### 应用本体

已经实现 HTTPS 更新清单、内置公钥、Tauri Minisign 验签、流式大小上限、安装前停止插件调用、失败恢复准入和重启。检查和安装阶段都会以目标 Desktop SemVer 重新验证当前签名插件集合，在下载前阻止会使插件被隔离的应用升级。正式验收仍需生产更新端点、真实签名密钥、代码签名证书以及从上一生产版本执行升级和失败回滚。

### 插件

已经实现短期签名目录、独立目录签名用途、精确大小/SHA-256、插件包二次验签、显式 Desktop SemVer 兼容范围、插件 SemVer 防降级、x86/x64 宿主预检、按插件维护、原子激活、热加载和崩溃恢复。控制器为活动路由保存完整插件清单快照，部署自检可识别服务数量相同但版本、入口、方法、参数等发生变化的磁盘漂移；它不会自动加载人工目录变化。管理员显式完整重扫时也先验签并逐组件启动候选宿主，全部成功后才替换活动路由。控制台的仓库检查操作不会安装：它展示当前版本、与当前 Desktop 兼容的最高版本，以及仅支持其他 Desktop 的仓库新版本；用户确认精确兼容版本后才进入安装流程。旧插件元数据可用于迁移诊断，但缺少兼容范围时不会进入运行路由或正式发布目录。签名插件还可由控制台显式卸载；卸载与本地映射删除都只排空目标插件，并通过可恢复事务一起切换目录和路由，避免直接删除造成崩溃后半完成状态。

面向整项目迁移的 `.ssdev-project` 使用独立 `project-bundle` 组织旁签绑定整个交付容器；正式客户端缺少旁签或遇到重新封包、错用途、吊销密钥时会在预检前失败。组织签名通过后，再在只读阶段联合验证来源授权覆盖、全部组件、路由和宿主，并展示配置更新、组件新增/升级/修复/替换及本机额外能力保留的变更计划。确认标识绑定项目包、Desktop 版本及目标机配置和全部组件内容，状态变化必须重新预检；复核通过后才以项目级持久提交点一起切换签名插件、本地映射、控制器路由和配置，提交前失败或崩溃整体回滚，提交后整体完成，不再保留逐组件成功导致的混合版本状态。

## 实际测试准入清单

1. 提供一套已脱敏的生产插件目录、代表性请求/响应和预期结果，生成覆盖所有 service/method 的黄金矩阵。
2. 在 Windows x64 真实设备上同时测试 32 位 DLL、已注册 OCX、硬件驱动和院内证书。
3. 提供业务前端产物和代表性账号 HAR，确认不再依赖 `7711`/`45121`；若仍有外部调用，再单独评审兼容适配器。
4. 配置非生产签名插件仓库和应用更新端点，先演练查询、指定版本安装、失败回滚与应用升级。
5. 生产发布前接入 KMS/HSM、公钥信任库、Windows 代码签名证书和真实上一版本安装包，完成灰度与回退演练。
