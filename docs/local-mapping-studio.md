# 本地原生映射工作台

控制窗口内置“DLL 动态映射与调试”工作台，用于项目现场接入新的 DLL、COM/OCX、EXE 或 BAT。它把原生接口的变化从 Rust 客户端发布周期中分离：只要现有调用模型能够表达厂商 ABI，管理员就可以选择组件、配置服务和方法、完成预检并立即热加载，不需要重新编译或重新安装 SSDEV Desktop。

## 使用流程

1. 新建映射并填写唯一的映射 ID 和显示名称。
2. 为每个接口填写 `serviceId`，选择 DLL/EXE/BAT 文件；工作台会只读检查 PE 标头，自动识别 x86/x64，并列出命名导出函数。COM/OCX 可直接填写 ProgID/CLSID，也可按当前服务架构搜索 Windows x86 或 x64 注册视图，再从结果选择版本 ProgID、组件类型和 CLSID。
3. 配置调用约定、字符集、超时和依赖文件，再把导出函数加入方法列表。
4. 为每个方法配置网页调用名、返回类型和参数。参数名以 `$` 开头时表示原生输出参数。COM/OCX 方法还可在“调用后读取属性”中逐项配置 `PROPERTYGET` 成员，现场调试结果会直接展示这些字段。`ReturnValue` 是宿主保留的原生返回字段，因此不能声明 `$ReturnValue`；COM 属性也不能使用 `ReturnValue`、与输出参数同名或彼此重名。保存、导入和签名前都会拒绝这些歧义声明，运行时仍会再次检查，绝不会用后写入字段静默覆盖已有结果。
5. 点击“保存、校验并热加载”。客户端会先复制组件到应用本地数据目录，在对应 x86/x64 隔离宿主中完成健康预检，再通过持久事务原子切换目录和路由；任一步失败都会保留旧映射，切换期间崩溃或断电也会在下次启动确定性回滚。
6. 在“现场调试”输入脱敏测试参数并运行。每次调用都会再次确认当前服务和方法属于该已批准本地映射，并在调用返回前固定当前能力集合，避免调试复核后并发插件切换把同名路由换成另一实现；界面会先提示可能触发打印、写卡或设备动作，再显示 `ResCode`、`ResData`、耗时以及“确认未执行 / 已返回 / 执行状态不确定”。只有收到完整宿主响应才会建议把状态码或安全的 `ReturnValue` 保存为期望值；不确定状态必须先核对设备和业务结果，不能直接重试。调试调用与业务调用经过同一 controller、超时、背压和隔离宿主，不存在另一套隐藏执行路径。
7. 为稳定场景填写用例名称、期望 `ResCode`，并按需启用“期望 ResData 子集”。成功调用后工作台只建议采用数值、布尔或 `null` 类型的 `ReturnValue`，不会自动保存字符串或完整响应；也可人工填写需要验证的脱敏输出字段。每个映射最多保存 32 个，用例只能引用已经声明的服务、方法和输入参数。
8. 点击“顺序运行全部”后，工作台会先明确提示这些用例可能触发打印、写卡或设备动作；确认正在使用测试设备和可回滚数据后，才固定当前能力集合并复用正式调用路径验证映射，批次结束前插件安装、删除和重扫会等待，不能在相邻用例间替换路由。controller 在本地管理调用中额外保留“确认未执行 / 已返回 / 执行状态不确定”三态，不根据可能与厂商返回值重叠的 `ResCode` 猜测。首个断言失败、确认未执行或执行状态不确定都会立即停止，剩余用例明确显示为未运行；状态不确定时先核对设备和业务结果，不能直接重试。对象断言只比较填写的字段，嵌套对象同样采用子集语义，数组与基础值精确比较。批量结果只保留执行状态、通过状态、实际/期望 `ResCode`、不匹配 JSON Pointer 路径和耗时，不返回或记录实际 `ResData`；顺序与失败即停共同避免多个用例继续争用或重复操作同一设备。
9. 在映射卡片点击“TS”可导出类型化客户端。生成文件从 `@bsoft/ssdev-web-bridge` 引用公共类型，为每个公开路由生成输入、`ReturnValue`、输出参数和 COM 属性，不依赖 Tauri 私有 API；同一文件另行导出 `create<Plugin>TrackedApi()`，为打印、写卡等非幂等流程生成相同参数/响应类型的持久调用和状态查询方法。方法勾选“业务调用必须使用持久操作 ID”后会写入 `trackedInvocationRequired: true`，普通 Client 不再生成该方法，运行时也会在原生宿主前拒绝普通业务调用；受控现场调试仍可执行。tracked 工厂只接受 SDK 已确认可用的 `TrackedInvocationBridge`，方法只接受由 `createPluginOperationId()` 创建或 `parsePluginOperationId()` 从业务记录严格恢复的 `PluginOperationId`；它不提供 ID 存储或自动重试。COM 属性在缺少静态类型声明时明确生成为 `JsonValue`，不会假装推断出厂商类型。常见单服务映射直接以公开 alias（没有 alias 时使用方法名）生成 `readCard()` 这类调用；无输入方法可以省略 `{}`。只有不同服务的公开方法重名时才增加服务前缀，清洗后仍冲突时才追加稳定序号；tracked 状态查询名还会避让所有调用方法，防止覆盖真实路由。`constructor` 和内部 `bridge` 成员会使用安全的 `invoke...` 名称，但底层 service/method 路由始终保持原声明。普通客户端只包含未强制持久调用的方法，构造函数仍只要求最小 `PluginInvoker`；前端单元测试可用 SDK 的 `createPluginFixtureInvoker` 精确匹配这些普通路由和完整 JSON 输入。fixture 不注入全局桥接、不模拟硬件、持久调用或崩溃恢复，不能替代正式插件矩阵。重新导出会采用当前命名规则，业务项目应把生成文件作为受控代码制品并随映射变更一起评审。
10. 现场验证稳定后点击“发布源”，选择一个受控父目录。客户端会创建新的 `<pluginId>-release-source` 目录，只写入 `api.json` 和清单实际引用的组件/依赖；同时在目录外生成 `<pluginId>-matrix-seed.json` 草稿，复用已保存的脱敏用例，并为尚未覆盖的方法补占位用例。随后把两者分别交给 `ssdev-plugin-tool prepare --source ... --matrix-seed ... --desktop-version-requirement ...`，由发布负责人明确填写已经验证的 Desktop SemVer 范围，再生成版本元数据、经强校验的黄金矩阵草稿和外部签名请求。

保存后的映射可继续编辑、删除，或导出为 `.ssdev-mapping`。删除不会只根据页面上的旧 ID 立即执行：Rust 先只读复核磁盘与活动路由，控制台在一次确认中展示将卸载的服务、方法、回归用例数量以及未保存草稿影响；计划标识绑定规范映射包内容、映射 ID 和 Desktop 版本。确认删除时会在安装锁内复算一次，进入目标维护窗口、排空调用后再复算一次；目录原子暂存到不可预测的事务位置后，还会对实际待删除字节计算第三次同一标识，不一致立即恢复原目录。任一内容、身份、隔离状态或运行路由漂移都停止删除并要求重新检查。复核通过后才继续目标映射自己的短维护窗口，并复用保存/导入所用的持久目录事务：路由提交前失败、进程崩溃或断电会恢复原映射，提交后只完成备份清理，不会让磁盘目录与活动路由永久分叉，也不会停止无关插件。映射包同时包含声明、本地组件和合成回归用例，另一台受控终端可从工作台导入。选择文件后只执行有界解包、清单/安全路径/声明架构与联合路由结构校验，不加载其中的 DLL/COM/EXE，也不改当前映射；控制台展示安装或替换动作、服务、声明架构、组件类型、方法数和用例数。用户明确确认信任未签名原生代码后，客户端重新读取同一文件，复算绑定包摘要、Desktop 版本和目标映射当前确定性内容的计划标识，再在对应架构隔离宿主实际加载 DLL/依赖并解析导出，或实例化 COM/OCX 并解析成员；EXE/BAT 只检查文件不执行。原生初始化和 Health 全部通过后才进入原子热加载。文件或目标映射在两步之间变化、同名签名插件/隔离目录冲突或活动路由漂移都会要求重新预检。TypeScript 导出采用不覆盖写入，已有目标文件需要由开发人员明确处理。

保存或导入后的映射使用 schema 2 `local-mapping-integrity.json` 固定 `api.json`、`plugin.json`、实际入口组件和依赖的大小及 SHA-256。插件发现会逐文件复核；控制器还把已批准的完整性文档摘要传给每次新启动的隔离宿主，宿主重新验证文档并把其中的逐文件 SHA-256 交给原生适配器。DLL 在预检后保持加载；EXE/BAT 入口在 Windows 宿主生命周期内保持不可写、不可删除，并在每次创建子进程前复算 SHA-256，运行期间漂移不会等到宿主重启才被发现。旧 schema 1 映射在启动恢复完成后执行一次受限迁移；schema 2 缺少清单或内容漂移只会被隔离，不会自动重建清单。调试用例保存在 `local-mapping.json`，不参与原生宿主完整性文档，但会进入本机能力基线的映射定义摘要；工作台保存或删除用例会以操作前摘要防并发覆盖并受控更新基线，客户端退出期间直接改写用例则在重新扫描确认前隔离映射并阻止回归执行。

编辑器以确定性声明内容跟踪当前草稿。“新建映射”、切换其他映射、导入映射包以及关闭控制窗口都会在存在未保存更改时提示；取消后保留当前草稿。编辑器提供明确的“放弃更改”入口，按最近保存基线恢复现有映射或空白新建状态；保存或导入成功才更新这条基线。已保存映射的 ID 是 Web 路由、Windows 目录和部署内容使用的稳定身份，编辑时固定不可改名；新 ID 只能使用 1–128 位 ASCII 字母、数字、点、短横线或下划线，不能以点开头或结尾，也不能命中 Windows 保留设备名。工作台在调用原生预检前提示，Rust 在映射保存、迁移包、项目包及恢复事务边界复用同一规则。需要新身份时必须新建映射，验证后再单独删除旧映射。新建草稿命中已有 ID（按 Windows 文件系统语义忽略 ASCII 大小写）时会明确展示替换影响并要求二次确认，确认后继续沿用磁盘中的规范大小写；Rust 同时拒绝直接创建仅大小写不同的第二个目录，避免非 Windows 开发环境产生无法部署到 Windows 的歧义状态。保存请求还声明编辑器预期目标应存在或不存在，Rust 在安装锁内、原生预检和目录切换之前重新核对；确认后目标被外部创建、移除或变成异常文件时保存失败关闭并要求重新读取，不能依据过期清单静默覆盖。调试用例使用独立持久命令保存或删除时，只同步基线中的用例集合，不会把尚未保存的服务、方法或 ABI 字段误标成已保存。当前映射存在草稿时，现场调用、用例保存/回归、TypeScript、迁移包和发布源均要求先保存并热加载；之前的调用与回归结果会立即失效，不能挂在新 ABI 表单下继续显示。其他没有草稿的已保存映射仍可独立导出；删除当前映射则单独确认草稿丢失。项目部署包成功导入后工作台会重新读取目标机映射清单；如果导入前存在未保存草稿，必须先明确确认丢弃，项目导入失败则不刷新编辑器。草稿存在期间，控制台还会暂停项目包生成/预检、签名插件安装/卸载/重扫/版本切换、应用更新和深度部署自检，并把首页部署结论标为不包含草稿；这些操作不能静默使用旧的已激活映射。保存或明确放弃草稿后门禁自动恢复，现有业务窗口维护、日志导出和按架构宿主恢复不受影响。

本地映射不能接管签名插件命名空间。签名插件根中只要存在同一 Windows 规范 ID 的目录，即使该目录当前验签、清单或兼容检查失败，本地映射在启动发现、保存、导入和重扫时都保持冲突状态。应先处理签名插件隔离项或为开发映射使用新 ID；不能通过损坏签名插件来把生产 Web 路由降级到开发实现。

映射保存、映射包导入和删除都把“原生能力已经提交”与“工作台重新读取清单”分开处理。Rust 命令成功后立即保留成功事实并通知全局控制台刷新；随后 15 秒内无法重新读取工作台清单时，不会把操作改报为失败，也不会建议重复提交。工作台和首页会标记“映射清单待复核”，暂停依赖该清单的编辑、调试和项目操作，并提供专用重新读取入口。重试成功后按实际磁盘定义恢复编辑器；保存/导入使用后端规范化后的组件路径，删除则按目标映射重建草稿基线。底层读取错误和路径不进入页面。

“发布源”与迁移包用途不同：待签名目录明确排除 `local-mapping.json`、本地 `plugin.json`、旧签名、未引用文件和合成调试用例。矩阵种子是目录外的独立发布输入，始终保持 `draft: true`，不会进入签名插件；它只减少重复录入。导出结果中的“占位待补”既包括没有现场用例的方法，也包括缺少声明输入，或虽有状态码用例但尚无完整 `ResData` 精确结果的用例；缺失输入使用显式保留标记补齐，绝不猜测 `0`、`false` 等可能产生真实副作用的值。所有转换用例还带有 `reviewRequired: true`，因为现场对象子集断言不能自动证明它就是正式完整响应。正式发布前必须完成输入和响应、逐项解除复核标记并解除草稿；运行器会在接触硬件前拒绝任一遗留门禁。任一目标已存在或父目录位于客户端管理的本地映射根目录时会拒绝写入；桌面端不接触私钥，也不直接制作可分发插件。

## 能力边界

- Windows 安装包同时携带 x86 和 x64 插件宿主，因此 x64 主程序可以调用 32 位 DLL；32 位安装包也保留双宿主。
- DLL 当前支持字符串、布尔、有符号/无符号 32 位整数、缓冲区输出和指针类返回。复杂结构体、回调函数、可变参数、厂商自定义内存释放或 GPU/驱动级上下文不能只靠表单安全推断，需要新增受审计的原生适配器。
- COM/OCX 通过 Windows 注册信息和自动化接口调用。仅有 `.ocx` 文件但尚未注册时，工作台不会替用户静默提权注册。
- COM 自动发现要求至少 2 个搜索字符，最多返回 100 项，并在 50,000 个注册类处停止。它只读取组件名称、ProgID、CLSID、注册架构和服务器类型，不创建 COM 实例、不读取服务器文件内容，也不从类型库猜测方法 ABI；方法、参数方向和副作用仍必须依据厂商文档配置并通过合成用例验证。
- COM/OCX 运行时同时接受 ProgID 和花括号形式的 CLSID。x86 与 x64 注册视图彼此独立；搜索结果为空时应先核对组件实际注册位数，而不是切换宿主后盲目重试。
- 通用 COM Automation 参数支持 BSTR 字符串、布尔、32 位有/无符号整数和双精度浮点，以及对应的 BYREF 输出；简写参数继续按输入值推断。插件准备、清单加载和 Windows 宿主使用同一份静态类型规则，无法表达的 VARIANT/结构体/数组/对象引用应改用专用 Rust 适配器。属性只允许 COM/OCX 声明，预检会解析成员但不会调用方法或读取属性。
- EXE/BAT 使用受限进程调用模型，不等价于任意命令行终端。
- PE 导出名称只能帮助建立候选方法，无法从二进制可靠推断参数 ABI。保存前必须依据厂商接口文档填写参数，现场调试也必须使用非生产、可回滚的数据。
- 通用 DLL 映射使用最多 12 个机器字参数的受限 ABI：输入支持字符串、布尔与 32 位有/无符号整数，输出支持最多 1 MiB 的字符串缓冲区与 32 位有符号整数，返回支持空值、字符串指针、布尔、整数和指针。浮点参数/返回、结构体、回调或所有权不明确的指针必须使用专用 Rust 适配器。相同静态规则由跨平台插件准备、清单加载和 Windows 原生宿主共同执行；类型名称会忽略首尾空格和 ASCII 大小写，但输出参数必须且只能有一个 `$` 前缀。
- 合成回归用例可以同时断言宿主级 `ResCode`、厂商 `ReturnValue` 和选定输出参数，用于发现路由、宿主、ABI 与业务结果退化。期望 `ResData` 限制为 64 KiB、16 层和 512 个节点；对象字段名和单个字符串也有上限，避免把大响应误存进部署配置。
- 本地用例采用子集断言，适合稳定状态码和关键输出；正式插件发布的黄金矩阵仍执行完整 `ResData` 精确比对，并生成绑定插件、源码和环境的机器证据，两者不能互相替代。
- 回归用例会随映射包和项目部署包迁移。不得把患者信息、真实账号、生产密钥或不可逆操作参数写入用例；打印、写卡等非幂等动作应使用专用测试设备和可回滚数据。批次停止只防止尚未开始的后续动作，不能撤销已经返回或执行状态不确定的设备操作。

## 信任与发布

本地映射是当前终端管理员明确创建或导入的配置，不是组织签名插件。它只能由内置控制窗口管理，文件被复制到固定的 `local-mappings` 应用数据目录，插件宿主只接受该根目录下的规范化子目录；业务 WebView 没有查看文件、导入、导出、保存、删除或调试权限。

`.ssdev-mapping` 适合受控项目现场之间迁移，但本身不提供发布者身份签名。预检计划证明“确认的文件和本机状态没有漂移”，不证明发布者身份。需要集中分发、版本治理、不可抵赖审计和自动更新的插件，仍应转换为 `.ssdev-plugin` 并通过组织签名仓库发布。不要导入来源不明的本地映射包，因为确认后其中的原生代码会在隔离宿主中执行。

本地完整性清单同样不是发布者签名：它固定 API、元数据、入口组件和依赖的运行内容。客户端还把已批准清单摘要、Web Bridge 声明和包含调试用例的规范化映射定义摘要写入本机插件能力基线 schema 4；已有 schema 1/2 基线升级时只对当前已验证映射做一次接纳，schema 3 只为内容与旧 API/版本/运行时摘要精确匹配的既有映射补入当前定义摘要。基线文件完全缺失时则不猜测“首次运行”，所有现存本地映射先隔离并要求人工确认。此后即使应用完全退出期间替换组件、完整性清单或仅改写调试参数，下一次启动、库存、项目导出、回归执行及部署自检也会隔离该映射。只有工作台保存/导入/删除/用例管理、项目原子切换，或管理员检查影响后明确确认完整重扫，才能以可恢复事务更新这条基线。

这仍然是本机批准状态而不是组织发布者身份：能够同时修改应用数据中的映射和能力基线的本机管理员仍可改写状态，明确确认完整重扫也表示接受当前候选。需要跨机器证明发布者、集中分发或自动更新时必须使用组织签名 `.ssdev-plugin`。
